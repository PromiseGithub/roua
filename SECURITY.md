# Security policy

ROUA exists to stop accounts from writing or reading secrets, so a flaw in it can give people false confidence. Reports are taken seriously and handled privately.

## What counts as a vulnerability

- `roua verify` or `roua audit` **passes** (no `fail`) for an account that can, in fact, change data or schema, or read a secret column it should not.
- SQL generated by `roua plan`, `roua apply` or the web generator grants more than the definition says, or can be injected into through any input.
- The web generator sends anything over the network, or leaks the password in any other way.
- A ROUA-App guard lets a `read_only` account perform a write, or lets a `sandbox` account reach a blocked route.

The known limits in [docs/threat-model.md](docs/threat-model.md), for example `NOTIFY`, or a secret stored under a column name the detector cannot recognize, are not vulnerabilities. Ideas to reduce them are welcome as ordinary issues.

## How to report

Use GitHub's private vulnerability reporting:
**https://github.com/PromiseGithub/roua/security/advisories/new**

Please include the PostgreSQL version, the roles and grants involved (a SQL script that recreates the situation is ideal), and the report output. Do not open a public issue for a vulnerability.

## What to expect

- Acknowledgement within 3 working days.
- An assessment and a planned fix date within 10 working days.
- Credit in the release notes and the advisory, if you want it.

## Supported versions

While the project is before 1.0, only the latest 0.x release receives fixes.
